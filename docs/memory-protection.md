# 内存压力保护

服务默认启用下列配置，旧配置文件省略 `Memory` 也会采用这些值：

```json
"Memory": {
  "SoftLimitPercent": 70,
  "RestartPercent": 90
}
```

- `SoftLimitPercent`：按宿主机总物理内存设置 Go 内存软限额，默认 70%。Go 会调整 GC 和内存归还，但这不是进程 RSS 硬上限，也不能回收仍被连接或缓存引用的数据。进程启动时已有的 `GOMEMLIMIT` 环境变量优先；设为 0 时恢复进程启动时的限额。Go 不会读取应用启动后才加载的 `.env` 中的 `GOMEMLIMIT`；这种情况会提示警告并继续使用自动软限额，请改用 systemd 服务环境或 `Memory.SoftLimitPercent`。
- `RestartPercent`：默认每 5 秒检查一次 `(Total - Available) / Total`，达到 90% 就记录诊断数据并退出。`Available` 包含可回收缓存，避免仅因文件缓存占用触发重启。采样失败不会触发退出。退出清理最多等待 10 秒，之后强制以状态 1 退出。

两项取值为 1–99，0 禁用对应保护；非零软限额必须低于非零重启阈值。配置热重载会更新保护参数，不额外创建监控任务。极低的软限额会增加 GC 开销，实际存活数据大于软限额时仍可能超过它。

自动拉起依赖服务管理器。安装脚本的 systemd 服务已有 `Restart=always`、`RestartSec=10`，所以检测后先退出，服务通常在退出后约 10 秒重新启动。手动运行、Docker 或其它管理器需设置自己的重启策略，否则程序只会退出。当前百分比针对宿主机；容器应另设适合容器额度的 `GOMEMLIMIT` 和管理器内存限制。

重启会中断本进程所有节点的现有连接。其它进程持续吃满内存也可能使程序重复退出；应同时查明占用来源，而非仅依赖重启。运行中的旧二进制不会获得此功能，需升级程序后才生效。

阈值日志包含宿主机总量/可用量、进程 RSS/swap、Go 堆分配/在用/空闲/已归还量、栈、goroutine 和 GC 次数，不包含用户身份或连接地址。用这些指标区分：

- 堆分配与 goroutine/连接数一起增长：排查并发连接和后台任务数量。
- 堆在用低、空闲堆高：排查峰值后保留及回收时机。
- RSS/swap 高于 Go 管理的内存：继续检查映射、原生分配和其它进程。

RSS 高或 swap 已使用不能单独证明内存泄漏；当前负载是否由换页造成还需对照换入/换出速率和内存压力记录。

本次修复了两处可复现问题：后台任务在回调中重启后可能重复执行；原生 AnyTLS 流未应用用户缓冲策略，在 amd64 上回退为每方向 512 KiB。AnyTLS 现在使用已有的 `ConnectionConfig.bufferSize`，默认每方向 64 KiB，慢连接达到队列上限后会阻塞生产者。该限制沿用 Xray 管道行为，单批写入可能超过上限，不是整个连接或进程的硬限额。这些缺陷不能单独认定为某次线上异常的根因；仍需结合实际版本、并发流数及堆数据验证。
